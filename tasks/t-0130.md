# A slow start is not a dead start, and a dead start is cleaned up

Starts on the cloud box are slow and the harness gives up too early, then
leaves the wreck on screen.

## Evidence

- Round r56: reviewer t-0124 was created 12:39:55Z; at 12:42:08Z the round
  recorded `no agent appeared in the reviewer's pane` (`src/round.rs` ~1559,
  `ReviewerState::Unstarted`) and started t-0125 instead. t-0124's pane was an
  empty bash prompt, yet `ha context` listed t-0124 as `[Working]` with
  status `failed` until it was resolved by hand. Round r57's reviewer t-0127
  needed more than two minutes for `pi` to appear in its pane on `oci`, and
  only just made it.
- `herdr-pro start` (`src/pro/lane.rs`, `ROLLOUT_TIMEOUT` = 180 s) gives up
  on a cold browser bridge, prints `WAITING ... the lane has no Codex rollout
  after 180s`, exits 0, and the lane is announced gone on the board while its
  Codex pane is alive and registers itself between 300 and 420 s later
  (reported from flyonenomics).

## What to build

1. Measure a real cold start of a `pi` lane and a reviewer on `oci`
   (`ssh remote-host`; the box is shared, leave nothing running) and set the start
   waits from what you measured, as event waits with an outer bound, not fixed
   sleeps. Put the measurements in the report.
2. A start that did fail is cleaned up the moment it is given up: its pane,
   tab and workspace are closed on the machine it ran on, its thread is marked
   failed, and it no longer shows as Working anywhere (context, overview,
   board, talk screen). A retried start does not leave two threads that look
   alive.
3. `herdr-pro start` never exits 0 on a lane it is about to call gone, and
   never calls a lane gone while its pane still runs Codex.
