## E6 — a refusal that worked is not a failure

```
f-0006 (9 times) retry — ha harness install: retry after command-failed
f-0005 (6 times) command-failed — ha harness install: harness_install_stale_self:
  this run installed a newer /home/agent/.local/bin/herdr-ade but is still the
  old process; run `ha harness install` again
```

`harness_install_stale_self` is D5's fix doing exactly what it was built to do.
It is a designed, correct, documented refusal with a next command in its message,
and the harness records it nine times as its own failure, at the top of the list,
above everything real.

The same shape appears in `f-0007`: `decision_authority`, the refusal that a
`what-you-get` decision needs a basis. Correct behaviour, counted as a defect.

The ledger cannot tell "the binary refused, and that refusal is the feature" from
"something went wrong". Give it that distinction. A refusal that the binary
itself raises on purpose is an outcome, not a failure; it may still be worth
counting somewhere, but it must not sit above a real defect in the list a
coordinator reads. Decide where the line is and say why in your report — a
refusal a person then worked around is different from one that resolved itself.

Do not solve it with a list of exempt strings. The binary knows which errors it
raises deliberately; make that knowledge structural.
