# A role can set the model a lane starts from

Rolf's decision, 2026-09-20: **a review starts from Sol.** Today it cannot.

## The problem

`src/launch.rs:245` is the whole recipe decision. Either the brief is `excluded`
— which resolves from `policy.pins`, a map keyed by the brief's SHA-256 — or Jev
scores it and `policy.select` maps the score to a band. There is no third path.

So the only way to put every review on Sol is to pin each review brief by hash as
it appears. That is a chore, not a policy, and it fails the first time someone
forgets. The reviewer role still exists (`src/threads.rs:223`, `:381`) and
`start_reviewer` in `src/round.rs` starts one with no recipe and `machine: None`,
so a review is scored exactly like any other lane. Under the current
cheap-by-default policy a review can be picked into DeepSeek.

## What to build

A per-role **floor** in `routing.json`, not a pin. "Starts from" is the
requirement: the role sets the lowest model a lane may be given, Jev still
scores the brief, and a score that lands higher still wins. Escalation must keep
working above the floor.

Suggested shape, but the exact key is yours to choose:

```json
"role_floors": { "reviewer": "pi_codex_sol_high" }
```

Requirements:

- A floor names a recipe that exists in the merged recipe map and is enabled;
  `validate_recipes` must refuse an unknown or disabled one the same way it
  refuses a bad route today (`src/routing.rs:119`).
- The floor raises a decision to that recipe's tier and never lowers one. A
  brief that scores into a higher band keeps the higher band.
- `escalation_exhausted` still means what it means: escalating from a floored
  lane looks for a strictly higher tier, as it does now.
- The dispatch row in `.state/dispatch.jsonl` must record that a floor applied
  and which role caused it, next to the existing `rule` field. A pick that was
  raised by a floor is not the same event as `jev-scores` and must not read as
  one in the ledger.
- No floor configured for a role means today's behaviour exactly. No default
  floors ship.

## Why a floor and not a pin

flyonenomics reports Sol reviews caught six real findings in their r23 and
restored records a lane had deleted in r26. That is outcome evidence, and it is
the reason for the decision. But a hard pin would also stop escalation taking a
review higher when it needs to go higher, and it would make the reviewer the one
role whose model no longer responds to the brief at all.

Do **not** reach the same effect by rewording the three scoring questions so that
review briefs happen to score high. A wrong MERGE genuinely is hard to undo, so
it would even be defensible, but tuning a rubric until it produces a routing that
was already decided is how the old rubric ended up measuring brief length.

One addition to your brief, from evidence that arrived after you started. Build the floor so it can be triggered by a question's answer as well as by a role.

The reason: irreversibility is a veto that I wrongly expressed as a weight. It carries 0.20 of 1.0, so it can move a score by at most 0.20. A task scoring maximum irreversibility and maximum subtle state with no invented design scores exactly 0.550, which is the top of the cheap band. A change that writes durable records other work reads therefore cannot escalate on that ground alone. Another project hit this tonight with two real lanes at 0.504 and 0.530, both writing validation records that a wrong value corrupts silently.

So a floor should be expressible as either a role or a condition on an answer — for example, irreversibility at its top level floors the lane at a named recipe. Same mechanism, same ledger requirement: the dispatch row records that a floor applied and what caused it. Keep the role floor for the reviewer exactly as briefed; this is an addition, not a replacement.

Do not solve this by raising the irreversibility weight. It is structurally a veto, not a compensating preference, and reweighting would distort every other decision to buy one behaviour. The TypeSafe guidance names this case directly: weighted scores suit compensating preferences, an any-serious-violation rule needs a separate condition.
A second addition, and this one closes a hole in what I briefed you. Evidence from another project that arrived after your first pass.

A floor keyed only on the round's own reviewer path will not hold. `round advance` can fail with `jev_server_refused: max_tokens_exceeded` — it has now done so on three consecutive rounds elsewhere, because the review brief embeds every lane report and grows with each admitted lane. When that happens the coordinator hand-starts the reviewer through an ordinary `ha thread start`, which takes an ordinary score. The rounds with the most lane output to review are therefore precisely the rounds routed by the cheap default. One of them took `pi_opencode_deepseek` to review a 268-line append to a durable validation record.

So the floor must apply wherever the work is identified as a review, not only where `start_reviewer` creates it. `ha thread start` already accepts `--workflow <FLOW>`, and its help text currently reads "Instruction set for this lane; this never selects its model". After this round that sentence is false and must be corrected in the same change — a tool whose help contradicts its behaviour is worse than one without the feature. Make a hand-started `--workflow reviewer` take the same floor as an automatically started one.

Related, and worth handling here if it is small: when the picker itself refuses an oversized brief it currently fails the dispatch rather than falling back. Falling back to the highest tier would lose nothing — three unrelated scoring designs ranked 90 briefs at or below a coin flip against our labels, so an unscored brief carries almost no information anyway — and it would stop the largest rounds from being the ones that silently get the cheapest reviewer.
