## What the harness is

herdr-ade (`ha`) runs Rolf's projects on the herdr screen server. Per project, a Claude
coordinator on the Mac turns Rolf's requests into tasks, starts helper lanes (pi on the box by
default; claude, agy and Pro on the Mac) through an editable routing table, batches finished
lanes into rounds that a separate reviewer checks, merges, pushes, and installs with
`ha harness install`, then proves each task's acceptance conditions with evidence. A ticker on
each machine watches and nudges; a courier brings box results home; hooks record Rolf's
request ids and check the coordinator's plain-language lines.

Rolf's direction (2026-09-21): a lean, stretchable meta harness. Editable routing and a small
core with adapters. Tasks tied to his requests. Finished, reviewed, merged, installed and
verified kept distinct. Typed results and a few recovery verbs. "Unknown" when evidence is
missing. Newer decisions win over stale memory. Small reviewed changes.

It grew fast: about 75,000 lines of Rust across rounds r66–r107 in two days, plus older
layers. Rolf says he no longer knows what is what.

## What to find

Everything that could be simpler or removed while every current function still works. For
example, but don't stop at these:

- commands, subcommands or flags that overlap, are rarely needed, or could be one verb;
- states, phases, groups and record files that say the same thing twice;
- specs, feature layers or modes that nothing uses any more (dialogue, board, routines,
  machine hold, terms, plan card, say/explain, checkpoint, legacy migrations, old-format
  readers);
- duplicated code paths (Mac vs box, local vs remote, thread vs round recovery);
- docs and skill text that repeat or contradict the code;
- tests that guard removed behaviour;
- things the coordinator must remember that the harness could do by itself.

For each finding, check it against the code before you write it. Say "unknown" where you
could not confirm.

## The report

Write it to the report path this brief names, in this order:

1. **In plain words** — at most ten short bullets Rolf can read in a minute: what to cut,
   what to merge, what to leave alone. No code names in this part unless unavoidable.
2. **Findings**, most valuable first. Each one: what it is (with `file:line`), why it is
   excess, the simpler shape, what function must still work and how that is kept, rough
   size (lines or files removed), and risk.
3. **Leave alone** — parts that look heavy but earn their place, and why.
4. **Order of work** — how you would split the cuts into small reviewed changes.
