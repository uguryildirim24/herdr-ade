# Stage discipline: four claims checked against the code

## H1 — real gap

**Truth.** `src/contracts.rs::PlanStep` stores id, text, projected state, bound tasks/threads and one level of subtasks, but no prerequisite. `src/plan.rs::project_states_with_evidence` and `derive_state_from_tasks` calculate completion from bound work; `with_subtasks_from_tasks` aggregates children. `src/cli.rs::ThreadCommand::Start` has no prerequisite input; `src/threads.rs::start_with_ticker` allocates/places work without reading the plan. `src/plan.rs::step_move` only changes display order. The claim is true: a coordinator can start stage B while A is left or running. `ha plan sync` and `ha plan show` expose the state, but cannot refuse a premature start. Manually checking them before each start is a usable habit, not enforcement, especially when multiple lanes start concurrently.

**Smallest change.** Add an optional `after: Vec<String>` to each existing `PlanStep` (empty by default so historical plans load). Extend `ha plan step add <project> "<text>" --task <job> --after <step>` (repeatable, works with `--under`) to store step ids; show them in `ha plan show`. Require the dependent step to have at least one bound stable task before its gate can affect launches. At `ha thread start <project> --job <job> --task-file <file>`, find every plan step binding that job (including historical `Task.plan_step`), take the union of its prerequisites, recompute their projected states from current evidence, and refuse before allocating a thread, pane or worktree unless every prerequisite is `done`. Recheck immediately before a deferred/unplaced start actually launches, so a delayed launch does not bypass a subsequently unsatisfied gate. No plan or dependency means current starts behave as they do now. A task bound to multiple steps must satisfy all their gates; starting another task in the prerequisite step remains allowed.

Refuse `--after` when the referenced step does not exist or the dependency is itself, cyclical, or would wait on its own parent/subtask; refuse removal of a step still referenced by an `after` edge (remove/rewrite the dependent step first). Refusal at start: `plan_prerequisite: <job> cannot start; step <dependent> waits for <prerequisite> (<left|running>). Finish the bound work and run ha plan sync <project>, or change the plan before starting.` Missing/unreadable evidence must never count as done. Record the edges in `plan.toml` and expose the blocking step ids in the refusal; do not add a thread status, another stage record, a supervisor, a free-form checklist gate or a workflow-specific state machine. A coordinator still decides which tasks bind to which step and whether a completed stage is scientifically sound; this only enforces an explicitly declared dependency.

**Regression.** With A bound to an unfinished task and B bound to another task with `--after A`, starting B is refused with no new thread; after A has positively satisfied evidence and a projection refresh, B starts. A delayed B start is rechecked at launch. Unknown/cyclic/self-referential and parent/subtask-waiting edges are refused; an old plan without edges still loads and starts normally.

## H2 — discipline, not code

**Truth.** `src/threads.rs::start_with_ticker` accepts `planner` and `critic` as workflows, but does not require approval of a lane's proposed plan before that lane runs. `src/review.rs::start_locked` collects sealed changed lanes; `selected` picks gates from changed paths; `prepare` dispatches a reviewer of the candidate diff; `verdict` checks the resulting sealed verdict and gates. That is post-work review, not pre-work plan supervision. The claim is true in the narrow sense, but a mandatory new role would add a second review path for a discretionary decision. Use `ha thread start ... --workflow planner` for a proposed plan, send it to a separate `--workflow critic` lane if independent scrutiny matters, inspect their reports, then start execution tasks. Where plan approval genuinely matters, wait for the finding before launching execution; no code and no universal supervisor gate.

## H3 — already covered

**Truth.** The exclusivity in the claim is wrong. `src/task.rs::add` and `drop_task` can create a request-backed task and retain a dated drop reason, but `src/note.rs::add` also appends a request-provenanced, optionally task-scoped **memory** note to `notes.jsonl` without creating a task; `rows` retains it, and `active_for` can carry it into later briefs (`src/thread.rs::brief_for`). The note can say “Proposed X as a follow-up; rejected because Y,” tied to the originating request and optionally the existing task: `ha note add <project> "Proposed X; rejected because Y" --kind memory --request <request-id> --task <job>`. `src/note.rs::validate_basis` requires an existing request; `retire` preserves history if it later becomes obsolete. If the proposal actually became a task, `ha task drop ... --reason` is the better record. Do not manufacture rejected tasks or a new proposal ledger. Recording every stray suggestion is a coordinator judgment, not an automatic event.

## H4 — discipline, not code

**Truth.** There is no single K-run-and-compare command. `src/cli.rs::ThreadCommand::Start` reads the task file afresh per invocation; `src/threads.rs::start_with_ticker` allocates a separate thread, saves its task bytes at `src/thread.rs::task_path_for_write`, binds it through `src/task.rs::link_attempt`, and `place_and_brief` stores a content-addressed frozen brief (`src/threads.rs`, `src/thread.rs::store_artifact`). These mechanisms already permit independent lanes with the same task file and explicit common base. They do not prove identical substantive inputs (current task notes and context may change), enforce distinct model/sample randomness, or compare reports. Full brief hashes necessarily differ across distinct tasks and lanes because each brief contains a task id and lane-specific report paths. `src/task.rs::view_with_evidence` uses only the **last** attempt to project one task's state: do not treat K concurrent runs under a single `--job` as K required results.

For replication that matters, create K stable tasks with the same request/acceptance, start K separate threads with the same unchanged task file and pinned integration base, save the K thread ids and frozen brief hashes, then give their sealed reports to a comparison lane with its own task. Use `ha thread show`/`ha task show` and the reports to verify the shared task text, acceptance and relevant context, then compare outcomes. Keep each frozen brief hash as provenance for its run; compare the shared content rather than expecting the full hashes to match. This is orchestration and scientific interpretation, not missing harness correctness. Recommend no code: a bulk launcher would not make runs independent or determine whether findings agree.

## Priority

Only H1 survives as a code change. Build its opt-in plan-step start gate first: it can prevent an actual premature launch, while H2 and H4 already have explicit lanes and H3 already has notes. This is a safety gate for declared dependencies, not a requirement that every project use stages.
